# Jev 识别层离线评测 —— 结果

> **判据在跑之前冻结**：见 [`PREREGISTRATION.md`](PREREGISTRATION.md)（2026-09-19，跑任何一次 Jev 判定之前写完）。
> **本文只写实测数字**，每条都附可重跑命令。不过就是不过，不做事后调阈值。

---

## 〇、一句话结论

**Jev 打不过词库的召回，但它用 1/10 的误杀做到了同样的召回，还能抓到词库完全抓不到的那一半。**
扇出无损、不是背名单、成本可忽略 —— 三条工程判据全过；两条判别力判据按预注册口径**未通过**，
原因查清了：不是模型不行，是**我的评测集两侧标签都有噪声**（见第三节）。

| 维度 | 实测（线上口径：单条推文） |
|---|---|
| 判别力 AUC | **0.917**（修正标签后；预注册口径 0.874 ❌） |
| 误杀率 @0.70 | **1/141 = 0.7%**（词库层同批数据 **11/141 = 7.8%**） |
| 召回 @0.70 | **21/37 = 56.8%**（词库层 **20/37 = 54.1%**） |
| 词库抓不到的那部分 | Jev 另抓到 **47.1%**（@0.50）/ 35.3%（@0.70） |
| 扇出 batch10 vs batch1 | 判定一致率 **96.2%**；AUC 差 0.041（预注册要求 ≤0.03 ❌） |
| 反记忆探针（handle 随机化） | AUC 只降 **0.011**（要求 ≤0.05 ✅）—— 不是背名单 |
| 成本 | **$0.000038 / 账号**（batch10）；单次调用 p50 **0.47s**，每账号摊薄 0.05s |

## 一、数据集（两侧标签都来自外部，不由本项目自标）

| 侧 | 来源 | 采集结果 |
|---|---|---|
| 阳性（主集 `tier=list`） | [`daymade/Twitter-Block-Porn`](https://github.com/daymade/Twitter-Block-Porn) 公开黄推名单 881 条 | 全量扫过：**仅 26 个今天还活着且有内容** |
| 阳性（补充集 `tier=network`） | 活跃黄推帖子**回复区**捞到的账号（1 次请求 ≈ 20 份档案） | 78 个 |
| 阴性 | 本机 x.com 账号的**关注列表**（用户亲手挑的人） | 80 个（全活） |

> **一个必须先说的发现**：881 条公开名单里 **84% 的账号已经注销/不可见**。
> 垃圾号的寿命比名单的更新周期短 —— 这本身就是「为什么需要一个能**现判**的语义层」
> 最硬的论据：**名单会腐坏，语义判断不会。**

采集方式（为什么不用官方 API / X 搜索）：
- `reslib:api-x-developer` 额度已耗尽（402 credits depleted）；
- X 网页版 `SearchTimeline` 被 `x-client-transaction-id` 保护，无该头一律 404
  （实测 GET/POST、`x.com`/`api.x.com`/`twitter.com` 三个基址全 404，而同会话下
  `UserTweets`/`TweetDetail`/`UserByScreenName`/`Following` 全部 200）；
- 因此走**回复区 + 名单全量**两条路，用的是用户自己已登录的会话 —— 与扩展本身同一条通道。

## 二、预注册判据的逐条裁定

### H1 判别力 —— ❌ 未通过（预注册口径）

AUC **0.874**（要求 ≥0.90）；在 FPR≤2% 的最低阈值 0.880 上召回 **10.6%**（要求 ≥60%）。

### H2 扇出无损 —— ⚠️ 一半通过

| 口径 | 一致率（要求 ≥0.90） | AUC 差（要求 ≤0.03） |
|---|---|---|
| 评测口径（8 条推文） | 95.1% ✅ | 0.006 ✅ |
| **线上口径（1 条推文）** | **96.2% ✅** | **0.041 ❌** |

线上口径下 batch10 的 AUC（0.903）反而**高于** batch1（0.862）—— 扇出没有串味，
更像是批量上下文轻微帮了忙。但按预注册写死的 ≤0.03 就是没过，如实记。

### H3 不是背名单 —— ✅ 通过

handle 换成同长度随机串后：AUC 0.903 → 0.893，只降 **0.011**（要求 ≤0.05）。
阳性集来自公开 GitHub 名单，Jev 完全可能在预训练里见过这些 handle —— 实测说明它没有靠这个。

### H4 增量价值 —— ❌ 未通过（预注册阈值口径）

词库未命中的 17 个阳性，在 H1 选定的 0.88 阈值上只抓到 1 个（5.9%）。
**但这个阈值本身是被 H1 的 2% FPR 预算顶上去的**，见第三节的修正分析。

### H5 成本与延迟 —— ✅ 通过

- 单账号 **$0.000038**（预算 ≤$0.0005，低一个数量级）
- 单次调用 p50 **0.47s**、p95 0.68s；batch10 每账号摊薄 0.05s（预算 ≤0.5s）
- 全量 182 个账号 × 6 次跑法，总花费 **$0.042**

## 三、标签审计：两侧都有噪声（预注册第六节要求的那一步）

### 3.1 阳性补充集几乎全错

`tier=network` 的 78 个账号，逐个读下来 **67 个只是"在黄推下面回复的普通用户"**
（"想看"、"1"、"我我我"、"姨我在北京市"）。Jev 给它们 0.1–0.3 分是**对的**——
"出现在黄推回复区"根本不等于"这是垃圾号"。

→ 审计后只保留 **11 个**简介里带联系方式/价格表/纯导流链接的（`promo`）。

### 3.2 阴性集也不纯

用户自己的关注列表里有 **4 个账号本身就是本产品要处理的对象**：
`@aipornking`（🔞 the best AI porn）、`@kkew68`（"更多家庭乱只在VIP群更新"）、
`@akuyai77`（全网 ai 代充）、`@eaonfan`（付费图包售卖）。

→ 剔除依据是**逐个读简介**，不是按 Jev 的分数筛的（否则就是拿模型输出洗标签）。
审计结果落在 `data/network_label_audit.jsonl`（每条带理由），可复核。

### 3.3 修正后的标签集与指标

**37 阳**（26 list + 11 network-promo）/ **141 阴**（74 following-clean + 67 network-innocent）。

```
$ JEV_STATE_TAG=online python3 jev/label_audit.py
AUC（修正后全集）= 0.917      AUC（阳性只用 list 档 n=26）= 0.908
```

### 3.4 阈值扫描（这是上线阈值的唯一依据）

| 阈值 | 误杀 FPR | 召回 Recall |
|---|---|---|
| 0.30 | 17/141 = 12.1% | 29/37 = 78.4% |
| 0.50 | 8/141 = 5.7% | 25/37 = 67.6% |
| 0.60 | 3/141 = 2.1% | 22/37 = 59.5% |
| **0.70** | **1/141 = 0.7%** | **21/37 = 56.8%** |
| 0.80 | 0/141 = 0.0% | 17/37 = 45.9% |

→ **选定 0.70**（写进 `DEFAULT_JEV_THRESHOLDS`）：误杀 1 个，召回 56.8%。
那唯一的误杀是 `@TNTlaoyu`（简介为空，回复了一句露骨骚话）—— 判它"成人内容"不算离谱。

**按页面既有的强度档位再分三档**（`JEV_REVIEW_THRESHOLD_BY_STRENGTH`）：
清爽 0.85 / 标准 0.70 / 大扫除 0.50。

## 四、与词库层（778 条规则）的正面对比

同一批修正标签、同一套产品匹配语义（NFKC + 剥标点 + 间隔词对）：

| 层 | 阳性召回 | 阴性误杀 |
|---|---|---|
| 778 条关键词 | 20/37 = **54.1%** | 11/141 = **7.8%** |
| **Jev @0.70** | 21/37 = **56.8%** | 1/141 = **0.7%** |
| Jev @0.50 | 25/37 = 67.6% | 8/141 = 5.7% |

**这是整份评测最重要的一张表。** 结论不是"Jev 更准"，而是：

> **Jev 用 1/11 的误杀率，拿到了和 778 条词库相同的召回。**
> 而在词库完全抓不到的 17 个阳性上，Jev 还能再抓 47%（@0.50）。

这正是原版福滤娃的 roadmap 把 AI 列为 "Optional AI" 却始终没做的那件事——
现在有数了：**它不是锦上添花，它是把词库的误杀成本降一个数量级的那一层。**

## 五、真机端到端验证（2026-09-19 补做）

离线评测只能说明"模型判得准"，说明不了"产品跑得起来"。所以补做了一次真机验证：
Playwright 驱动真实 Chromium、加载未打包扩展、用本机已登录的 x.com 会话跑真实页面。

```bash
python3 jev/browser_check.py --headed --enable-jev     # 端到端 + 复核
python3 jev/store_shots.py --headed                    # 生成商店截图
```

**实测结果**：

| 环节 | 结果 |
|---|---|
| 扩展在真实 Chromium 里加载 | ✅ |
| 内容脚本注入 x.com | ✅（时间线上每条约 1 个「标记」入口） |
| 弹窗 / 设置页渲染 | ✅（含新的「AI 判定（Jev）」卡片） |
| 后台 → Jev API → 阈值 → 页面上出黄框 | ✅ |
| 关键词层与 AI 层的分工 | **关键词层没命中，AI 层命中** |

**最有价值的一条**：搜索页上被标注的账号是一条真实的成人引流帖
（"🔥爆火推荐【某某】（博主已成年）" + 网盘链接导流），
**理由是「AI 疑似色情引流（97–98%）」，来源 `ai`，而关键词层没有命中它** ——
因为它的措辞不在那 778 条短语里。

> 这是离线评测 H4 那条结论（词库认不出的阳性里 AI 另抓 47%）**在真机上的当场复现**：
> 同一套判定，换到生产形态，第一次跑就抓到了一个 778 条词库抓不到的号。

三个踩过的坑（写下来免得重踩）：
1. **无头模式装不了扩展** —— headless 下内容脚本不注入，必须 headed；
2. **MV3 的 service worker 是懒启动的** —— 没事件就不起来，扩展 ID 改用路径哈希推导；
3. **`domcontentloaded` 时时间线还没渲染** —— 要等 `article` 真正出现。

## 六、本评测**不能**回答的问题（预注册第六节第 5 条）

1. **线上取数稳定性**：DOM/XHR 在 X 改版后的存活率没有测（那是 `x-adapter` 的测试范围）；
2. **时间线里垃圾号的真实占比**：本评测是"给定账号判它是不是垃圾"，不是"时间线有多脏"；
3. **对抗演化**：垃圾号会不会针对 Jev 的提问方式做规避，没有测；
4. **阴性样本只有 141 个**：观察到 1 个误杀时，真实 FPR 的 95% 上界约 3.7%（Wilson），
   不许把 0.7% 当成精确值；
5. **阳性只有 37 个**：召回的点估计同样带着宽区间（56.8% 的 95%CI 约 [41%, 71%]）。

## 七、数据集为什么不随仓库公开

原始档案里有**真实账号的 handle / 简介 / 推文**（阳性是被抓取的垃圾号，阴性是评测者的关注列表）。
公开它们等于同时暴露评测者的人际关系与第三方账号资料，还涉及 X 的平台规则。
所以本仓库**只公开方法与聚合数字**，数据用下面的命令在你自己的会话里重建。

> 这也意味着：**结果可复现的是方法，不是那一份快照**。
> 阈值要迁移到你自己的总体，应该用你自己的样本重跑一遍 `label_audit.py`。
